## חלק 1 — פילוסופיית המוצר והמערכת

### 1.1 מטרת המערכת

המערכת היא **צינור אוטומציה שיווקית** המתעד את כל מחזור החיים של פנייה ללקוח: מי הישות, איזה טלפון, איזו פעולה בוצעה כלפיה, באיזו תוצאה, ואם הפעולה נכשלה — האם נדרשת התערבות אנושית. כל המידע הוא **חסר-סודות** ברמת הקוד — מספרים שלמים אטומים מייצגים לקוחות, מילון נתונים מבוקר מייצג סוגי-ישות, וכל המחרוזות העבריות שלקוחות מצופים לראות יושבות בלעדית ב-`frontend/src/config/strings.he.js` וב-`clientRegistry.js`.

### 1.2 המעבר מ-Phone-centric ל-Entity-centric (Phase E2)

המערכת נולדה כ-Phone-centric: הטלפון היה ה-PK של הצינור והישות (`Entity`) הומצאה אחרי שטלפון נוצר. מודל זה נשבר ברגע שלקוח רצה לתעד **אדם או חברה ללא טלפון מוכר** (למשל לפני שמספר מאומת, או בלידים שמגיעים בעיבוד אצווה). המעבר ל-Entity-centric עיגן את ה-`Entity` כתחנת המוצא:

- **`Entity`** נוצר תמיד תחילה ולעולם לא תלוי בטלפון.
- **`PhoneNumber`** הוא ילד של `Entity` (יחס one-to-many דרך `entity_id`).
- ישות יכולה להיות **`primary`** או **`associated`** — האחרונה מצביעה על ישות שורש דרך `target_entity_id` (relation_type נמצא ב-`extra_data` של הישות עצמה כדי לאפשר להחליף את אוצר-המילים מבלי לנדנד את הסכימה).
- "אקסיומה של ירושה": phone שמותקן על ישות `associated` יורש מהשורש את `customer_tier` בעת חישוב ניקוד עדיפות (Phase DY, `envelope_propagation`).

המעבר משחרר את הצינור מתלות בטלפון ובאותו זמן מאפשר תיעוד full-graph של מי קשור למי לפני שטלפונים נכנסים בכלל לתמונה.

### 1.3 ניקוד עדיפות ו-Tiers (Phase DY)

עדיפות מחושבת לפי שני "וקטורים":

- **Vector A — Identity / Verification**: האם הישות מזוהה במלואה (`identity_verdict` ב-`extra_data`), חלקית (שם בלבד), או נדחתה.
- **Vector B — Relation envelope**: כשהישות היא `associated`, מהי דרגת ה-customer_tier של השורש.

ה-`PriorityScoringStrategy` (`backend/modules/mock_scoring.py`) מחבר את שני הוקטורים לפי נוסחה ניתנת-להחלפה דרך משתנה הסביבה `SCORING_MODULE`. הציון מתורגם ל-**Tier**: ‎`bronze | silver | gold | platinum`‏. ה-tier משמש את ה-UI לסידור ולסימון; ה-priority_score עצמו משמש את הצינור (`ORDER BY priority_score DESC NULLS LAST`).

### 1.4 חריגי-צינור = `PipelineTask` (Phase DX)

לא כל מצב הוא success-path. כשפעולה נכשלת ("provider_blocked", "quota_exceeded"), כש-מנהל מתבקש לאשר פעולה ספציפית, או כשהמערכת ממליצה על בדיקת איכות ידנית — נוצרת **`PipelineTask`** עם אחד משלושת `task_type`:

- `remediation_failure` — אוטומטי, ע"י retry_engine, אחרי כישלון.
- `approval_required` — בקשת operator לקבלת אישור מנהל לפעולה רגישה.
- `manual_recommendation` — הצעה של מנוע verification לסקירת איכות.

המשימה מוצגת ב-**Task Center** (`/operations`) שמוגן ב-`RequireRole role="admin"`. הסיום הוא בשני סטטוסים טרמינליים: `resolved` או `rejected`, עם הערה אופציונלית. תמיכה ב-Bulk update נוספה ב-Task Center enhancements.

### 1.5 ה-"Secrets-Free Mandate"

עיקרון ארכיטקטוני מנחה: **ה-backend לא יודע אף שם של לקוח אמיתי, סוג-פעולה אמיתי, טמפלייט הודעה אמיתי, או ערוץ צ'אט אמיתי.** הוא מכיר רק:
- `client_id: int` אטום (1, 2, 3...)
- `relation_type: str` מתוך אוצר-מילים מבוקר ב-`interfaces/relation_types.py`
- שדות אטומים ב-`extra_data: dict` (JSON) של כל מודל

הפענוח לעולם החיצוני קורה רק ב-frontend (ב-`clientRegistry.js`, `chatChannelRegistry.js`, `notificationEventCatalog.js`, `actionTypeIcons.js`). מסר זה משמעותי לאינטגרציה בארגון מסווג: כל המידע המסווג מוזרק ברמת ה-Configuration, לא ברמת הקוד.

### 1.6 ארכיטקטורת הרשאות — guardrails לא חומת אש

המודל המוסכם: **role-check לבטיחות ולמניעת טעויות, לא הגנה מפני שחקנים זדוניים פנימיים** (כל העובדים מהימנים). מימוש מינימליסטי:

- Session על HttpOnly + SameSite=Lax cookie (`marketing_session`), ללא JWT, ללא CSRF tokens.
- `admins.json` סטטי בקובץ, מסונכרן ל-`user` table ב-startup דרך `services/admin_sync.py`.
- שלוש פעולות-מצב: `unauthenticated`, `guest`, `authenticated` (כש-authenticated מתפצל בין `role=admin` ו-`role=regular`).
- Frontend route-gate (`RequireRole`) + backend dependency-gate (`require_admin`) — אכיפה כפולה.
- Personalization toggle (`AUTH-C`) — אופציה למשתמש לסנן ל-`managed_client_ids` שלו על כל המסכים, מנהלים אמורים לראות הכל אבל יכולים לבחור פוקוס.

### 2.3 דפוסי עיצוב ארכיטקטוניים

**Strategy Pattern (Plugin-via-env)** — לוגיקה עסקית מוזרקת ב-runtime דרך משתני סביבה. ב-`dependencies.py` שלוש "abstract base classes" מתממשות במודולים שניתנים להחלפה:

- `BaseScoringStrategy` (`interfaces/scoring.py`) → `mock_scoring.py` או הזרקת PriorityScoringStrategy אמיתי דרך `SCORING_MODULE=path.to.real`
- `BaseIngestionRoutingEngine` (`interfaces/ingestion.py`) → `mock_ingestion.py` או אחר דרך `INGESTION_MODULE`
- `BaseNotificationChannel` (`interfaces/notifications.py`) → `mock_chat.py` או אחר דרך `NOTIFICATION_MODULE`
- `BaseActionHandler` (`interfaces/dispatcher.py`) → `mock_dispatcher.py` או אחר דרך `DISPATCHER_MODULE`

**Service Layer Pattern** — כל הכתיבה ל-DB עוברת דרך service יחיד לכל טבלה:

- `services/auth.py` — sessions + login/logout
- `services/user.py` — user CRUD + managed_client_ids
- `services/entity_ingestion.py` — Entity ו-PhoneNumber writes
- `services/bulk_ingestion.py` — bulk-text + bulk-file parsing + writes
- `services/tasks.py` — PipelineTask lifecycle
- `services/notifications.py` — subscription rules + delivery audit
- `services/scoring.py` — חישוב priority + tier
- `services/verification.py` — בדיקות לאחר ingestion
- `services/dispatcher.py` — שליחת פעולות לערוצים
- `services/export.py` — Excel export builder
- `services/admin_sync.py` — סנכרון `admins.json` ל-`user` table

מימוש ה-service אף פעם לא מסתמך על FastAPI dependencies; מקבל `Session` ופרמטרים פשוטים. זה משמר את היכולת לבדוק כל service ביחידה ב-pytest ללא הרמת אפליקציה.

**Repository / Service-as-sole-writer** — אין SQL ישיר מ-endpoint או מ-script; אחת ה-services היא הכותב היחיד לטבלה. בקשות API קוראות `service.do_thing(session, ...)` ועוטפות ב-Pydantic response.

**Adapter Pattern** ב-frontend — תרגום בין shape של ה-API ל-shape של ה-UI נמצא ב-`frontend/src/api/adapters/`:
- `phoneAdapter.js` — `enrichPhone`, `enrichPhoneList`
- `taskAdapter.js` — `enrichTask`, `enrichTaskList`
- `paginationAdapter.js` — `unwrapPage`
- `schemaAdapter.js` — schema → UI hints

**ABC contracts** — קבצי `interfaces/` מגדירים חוזה אבסטרקטי שכל מימוש חייב לקיים. `tests/unit/test_abc_contracts.py` בודק שמימושי mock פועלים לפי החוזה.

### 2.5 שכבת תקשורת

- **HTTP** — REST פשוט, `/api/v1` prefix, JSON in/out, Excel out רק בנקודת `/{table}/export`.
- **Auth** — HttpOnly cookie בלבד. ה-axios `withCredentials: true` מפעיל שליחה אוטומטית.
- **Correlation ID** — `X-Request-ID` נשתל ב-`apiClient.interceptors.request` (UUID per request), נשמר ב-`ApiError.requestId` לתחקור log-to-toast.
- **Repeat-param arrays** — `paramsSerializer: { indexes: null }` ב-axios; FastAPI `list[int] = Query(None)` קורא רק את הפורמט הזה.
- **Pagination** — backend מחזיר `{items, total, page, page_size}`; frontend עוטף ב-`unwrapPage`.

## חלק 5 — מדריך אינטגרציה לסביבת פרודקשן

### 5.1 החלפת DB (SQLite → Postgres ארגוני)

**מיקום יחיד**: `backend/config.py`.

```python
class Settings(BaseSettings):
    database_url: str = "sqlite:///app.db"   # ←  שנה כאן
```

**שיטה מומלצת**: הזרק `DATABASE_URL` ממשתנה סביבה. אל תערוך את הקובץ — Pydantic-settings קוראת אוטומטית מ-env. דוגמה:

```bash
DATABASE_URL=postgresql+psycopg2://user:pass@prod-host:5432/marketing
```

ה-engine ב-`backend/database.py` קורא בעקיפין ‎`settings.database_url`‏, אז אין שינויי קוד נוספים.

**שלוש נקודות לבדיקה לפני go-live**:
1. **`UTCDateTime` TypeDecorator** ב-`models/types.py` — מתאמת בין SQLite/Postgres בקריאה. Postgres מאחסן timezone-aware natively, אז זה pass-through. אין שינוי נדרש.
2. **`create_db_and_tables()` ב-`main.py`** — `CREATE TABLE IF NOT EXISTS` בלבד. **לפרודקשן: הוצא את זה מ-`on_startup` והעבר ל-Alembic migrations.**
3. **`extra_data: dict`** ב-SQLModel ממופה ל-JSON ב-SQLite, ל-`JSONB` ב-Postgres אם תגדיר את ה-Column עם `sa_column=Column(JSONB)`. ראה הערה בסעיף הבא.

### 5.2 הוספת שדות מסווגים — שלוש דרכים

#### דרך A: שדה נסתר ב-`extra_data` (המומלצת ל-MVP)

**אין שינוי בסכימה**. כל מודל בעל `extra_data: dict`. הוסף את השדה הסודי כ-key:

```python
# Backend service that writes the field:
entity.extra_data["national_id_classified"] = payload.national_id

# Backend service that reads (no schema change):
classified = entity.extra_data.get("national_id_classified")
```

**מתי להשתמש**: שדה אופציונלי, לא משמש לסינון אגרסיבי, לא דורש index. השדה לא יוצג באוטומציה ב-UI; ה-frontend יקרא אותו רק אם תוסיף לו פענוח ב-`exportCatalog.js` או ב-component ייעודי.

**זרימה הולכת לאיבוד**: ה-`enrichPhone` adapter ב-`frontend/src/api/adapters/phoneAdapter.js` לא יודע על השדה אוטומטית. הוסף בו mapping אם רוצים להציג.

#### דרך B: עמודה ייעודית בטבלה (לסינון רחב או index)

ארבעה קבצים לערוך, סדר חשוב:

**1. הוסף ל-SQLModel** (`backend/models/phone_number.py` למשל):
```python
class PhoneNumber(SQLModel, table=True):
    ...
    classified_field: Optional[str] = Field(default=None, index=True)
```

**2. הוסף Alembic migration** (אחרי שעברנו מ-`create_all`):
```bash
alembic revision --autogenerate -m "add classified_field"
```

**3. הוסף ל-Pydantic schema של ה-request אם ניתן ל-ingestion** (`backend/schemas/ingestion.py`):
```python
class SinglePhoneRequest(BaseModel):
    ...
    classified_field: Optional[str] = None
```

**4. עדכן את ה-service** (`backend/services/entity_ingestion.py` או `services/ingestion.py`):
```python
phone = PhoneNumber(
    ...
    classified_field=payload.classified_field,

```

**5. אם השדה נדרש בייצוא**: הוסף ל-`backend/services/export.py::_phone_filter_clauses` או ל-`exportCatalog.js`:
```js
// frontend/src/config/exportCatalog.js

  key: 'classified_field',
  label: 'שדה מסווג',
  format: 'text',
  defaultSelected: false,

```

**6. אם נדרש סינון מהיר ב-frontend**: הוסף ל-`PhoneTable.applyFilters` (`frontend/src/components/phones/PhoneTable.jsx`) + ל-`PhoneFilterBar.jsx` שדה UI.

**7. בדיקות**:
- backend: הוסף בדיקה ב-`tests/service/test_entity_ingestion_service.py` שהשדה נשמר.
- backend: הוסף assertion ב-`tests/api/test_endpoints.py` שהשדה מסתנן.
- frontend: הוסף case ב-`tests/unit/PhoneTable.applyFilters.test.js`.

#### דרך C: שדה רק על משתמש (`User`)

`User.managed_client_ids_json` כבר מדגים את הדפוס. אם תרצה להוסיף, למשל, `User.security_clearance_level: int`:

### 5.3 חיווט אינטגרציות חיצוניות

#### 5.3.1 ערוץ צ'אט פרודקשן (NotificationChannel)

**הקובץ להחלפה**: `backend/modules/mock_chat.py`. נעתיק את החוזה:

```python
class BaseNotificationChannel(ABC):
    @abstractmethod
    def send(self, event: str, recipient: str, body: dict) -> DeliveryResult: ...
```

**צור** `backend/modules/enterprise_chat.py`:

```python
from interfaces.notifications import BaseNotificationChannel, DeliveryResult

class EnterpriseChatChannel(BaseNotificationChannel):
    def __init__(self, base_url: str, api_token: str):
        self.client = requests.Session()
        self.client.headers["Authorization"] = f"Bearer {api_token}"
        self.base_url = base_url

    def send(self, event, recipient, body):
        resp = self.client.post(
            f"{self.base_url}/chat/{recipient}",
            json={"event": event, "payload": body},
            timeout=10,
        )
        return DeliveryResult(
            status="sent" if resp.ok else "failed",
            response_payload=resp.json() if resp.headers.get("content-type","" ).startswith("application/json") else {"raw": resp.text},
        )
```

**הפעלה** דרך משתני סביבה (`backend/config.py` כבר תומך):
```bash
NOTIFICATION_MODULE=modules.enterprise_chat:EnterpriseChatChannel
ENTERPRISE_CHAT_BASE_URL=https://chat.internal.corp/api
ENTERPRISE_CHAT_TOKEN=...
```

`backend/dependencies.py::get_notification_channel()` קורא לערך ‎`NOTIFICATION_MODULE`‏ ועושה `importlib.import_module(...)`. אין שינוי קוד נוסף נדרש מה-endpoint עצמו.

**אזהרה**: אל תכניס את ה-token לקוד או לקובץ .env שעולה ל-Git. השתמש ב-secret manager של הארגון (vault, AWS Secrets Manager, וכו').

#### 5.3.2 רישום לקוחות אמיתי (Client Registry)

הקטלוג הקיים — `frontend/src/config/clientRegistry.js` — מקוד-קשיח עם 5 לקוחות-דמו. ל-200+ לקוחות:

**שלוש אפשרויות, מומלץ #2**:

1. **תצורה סטטית מורחבת**: ערוך את `clientRegistry.js` ידנית. עובד עד ~50 לקוחות.

2. **שליפה מ-backend בעת boot (מומלץ)** — ה-backend לא יודע על שמות-לקוחות, אז ה-backend לא יכול לחזיר אותם. במקום זאת:
   - הוסף endpoint חדש `GET /api/v1/clients/registry` שמחזיר JSON של `{id, name, shortName, slaHours, ...}` מתוך **תצורת deployment** (קובץ `clients.json` נפרד, או DB משלך).
   - ב-frontend, החלף את ה-import של `CLIENT_REGISTRY` ב-`useClientRegistry()` hook שעושה fetch בעלייה ושומר במ-context.
   - שמור על אותו ה-shape כדי שכל ה-`getClientById` ו-`ClientMultiPicker` יעבדו ללא שינוי.

3. **טעינה דינמית מ-Active Directory / LDAP**: אם הלקוחות הם קבוצות AD, צור backend adapter שמרענן את ה-registry מ-AD ושירות `/clients/registry` משמש כ-cache.

**שינויים מינימליים בקוד עבור אופציה 2**:

ב-`backend/app/api/v1/endpoints/`, הוסף `clients.py`:
```python
@router.get("/clients/registry")
def get_client_registry() -> list[ClientEntry]:

```

ב-`frontend/src/api/`, הוסף `clientsApi.js`:

```js
  const { data } = await apiClient.get('/clients/registry');

```

ב-`frontend/src/contexts/MockDataContext.jsx`, החלף את `clients: CLIENT_REGISTRY` (שורה 121) ב-fetch ב-boot:
```js

```

`ClientMultiPicker.jsx` עדיין יקבל את ה-shape הזהה.

#### 5.3.3 הזרקת admins.json לארגון

הנתיב הנוכחי: `backend/config.py::admin_config_path = "admins.json"`. שלוש אפשרויות:

1. **קובץ ב-secret-volume** (Kubernetes secret mounted as file) — שנה `ADMIN_CONFIG_PATH=/var/secrets/admins.json`.

2. **AD / SSO Integration** — החלף את `services/admin_sync.py::sync_admins()` במימוש שקורא קבוצת AD. החוזה (`{username, password_hash | ad_principal}`) עובר ללא שינוי לטבלה. השתמש בפרוטוקול SAML/OIDC במקום password_hash.

3. **קובץ מוצפן** עם פתיחה ב-boot — שלב פיענוח ב-`admin_sync.py::_load_admins_file()` ב-בודק ל-stream מוצפן.
